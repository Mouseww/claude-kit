# Fleet Engineering

Fleet engineering is **agent-first development at team scale**: multiple humans, each with their
own agents, working in parallel branches, without corrupting each other's code or docs. It extends
harness engineering (the solo methodology) with mechanical, conflict-free-by-construction
coordination. See `references/rationale.md` for the full narrative, the twelve core principles,
and the comparison with harness-engineering. This methodology is language-agnostic; stack-specific
guidance loads lazily from `stacks/{stack}/` only when that directory exists.

## Step 0: Preflight (every request starts here, before any document is written)

1. **AGENTS.md**: if it exists, read it first. If not, this is a fresh project; see "Project
   Initialization" below.
2. **Degraded mode check**: if `tools/docs_lint.py` or `docs/exec-plans/` is missing, degraded mode
   is active. State this, name the missing piece, and point to `/fleet-engineering:init`. Then
   skip `docs_lint.py` and conflict detection (report both unavailable), write any required docs
   straight into `docs/` with no index generation, and run Step E as Core DoD only, one round.
   Never a reason to skip the evaluator entirely.
3. **Conflict detection** (full harness only): `git fetch --all --prune`, enumerate `origin/*`
   branches and open PRs (when a PR CLI is available), and read each one's
   `docs/exec-plans/active/*.md`. Compare your intended scope against their Claims: coarse check on
   the first two path segments, fine glob overlap only on a coarse hit. On overlap, STOP and surface
   it to the user; a human decides. No exec plans discoverable anywhere means "not available", not a
   failure. Details: `references/collaboration-controls.md`.

## Classify the Change

Derive five signals from `git diff origin/main...HEAD` and declare them in the PR description
(and the exec plan, if one exists):

| ID | Signal |
|----|--------|
| S1 | Adds or changes a public interface (exported symbol, endpoint, CLI flag, message contract) |
| S2 | Changes a persistence or wire model (schema, migration, serialization format) |
| S3 | Adds a new external dependency |
| S4 | Net added lines in non-test, non-doc files exceeds 150 |
| S5 | Changes behaviour an existing product spec describes |

Routing, read top to bottom, first matching row wins:
- **Core**: S1-S5 all false. No artifacts; implement, audit, PR.
- **Design**: S1, S2, or S3 true, and S4 and S5 both false. Design doc required.
- **Full**: S4 or S5 true. Design doc + exec plan required, plus product spec when S5 is true.

The evaluator recomputes all five signals independently from the diff; any mismatch between your
declared and recomputed values is a MAJOR finding, which keeps classification from being self-adjudicated.

## Document Identity

Never invent an identifier by counting files in a directory; that single-writer assumption is what
this methodology exists to remove.

- Exec plan `docs/exec-plans/active/{TICKET}-{slug}.md`; with no ticket system, `{YYYYMMDD}-{author}-{slug}`
- Tech debt one file per entry, `docs/tech-debt/TD-{TICKET}.md` (`-a`, `-b` when several share a ticket)
- Quality one file per area, `docs/quality/{area}.md`
- Index pages and `docs/QUALITY_SCORE.md` are GENERATED by `docs_lint.py --fix`; a hook blocks hand-edits
- Every doc carries YAML frontmatter (type, title, status, owner, ticket, created, updated); schema in `references/docs-automation.md`

## Development Request Procedure

1. **Author required docs first, on the branch you'll implement on.** Status starts `Draft`, then
   `In Review` once the docs are complete (implementation may now start on the same branch).
   `Approved` is set by the human PR reviewer (or merge automation), never by you.
2. **Implement**, phase by phase, inside your declared claims. Run format, build
   (warnings-as-errors), and tests after each phase.
3. **Design turns out wrong mid-implementation?** Stop that deliverable, update the doc on the
   same branch, append a `Design Change` entry (what it said, what you found, what it says now,
   why) to the exec plan or PR description, reset status to `In Review`, resume. This entry is
   what tells the evaluator this was legitimate evolution, not post-hoc alignment. Full mechanics:
   `references/development-workflow.md`.
4. **Step E audit, per phase, mandatory:**
   - Bookkeeping first: check off deliverables, update design/spec if behaviour changed, update
     `docs/quality/{area}.md`, log tech debt for shortcuts, run `docs_lint.py --fix` then `--check`.
   - Spawn the evaluator: `subagent_type: "fleet-evaluator"` if the repo has
     `.claude/agents/fleet-evaluator.md`, otherwise `subagent_type: "fleet-engineering:fleet-evaluator"`
     (the plugin-provided one). Include change type, doc paths, changed files, round number, and
     (round > 1) prior findings with your fix/rebuttal.
   - The evaluator compares against the `origin/main` version of each doc, not your working copy;
     a doc changed on your branch without a matching Design Change entry is a MAJOR finding. It
     trusts your reported build/test evidence unless it's missing or contradicted, re-running only
     then; secrets scanning always runs directly.
   - Round 2, if needed, uses an explicit lens (`correctness`, `security`, or `contract-drift`)
     different from round 1; round 3 uses the last unused lens. Max 3 rounds; PASS needs zero
     BLOCKER/MAJOR; two identical consecutive FAILs also stop the loop. Only the user may authorize
     proceeding without PASS, logged as tech debt; you never propose it.
5. **One branch, one PR.** Docs and code ship together; open the PR only after evaluator PASS.
   CODEOWNERS routes doc changes to doc owners for semantic review.

## Definition of Done

**Core** (every change): build passes (warnings-as-errors), tests pass, formatting/architecture
checks pass, no secrets, evaluator PASS or a user-authorized skip logged as tech debt, the five
signals declared and matching the diff.

**+ Design tier** (design doc required): design doc reflects what was built with Design Change
entries for every divergence; `docs/quality/{area}.md` updated.

**+ Full tier** (spec + plan required): spec reflects actual behaviour; exec plan deliverables
checked off and moved to `completed/` when done; `docs_lint.py --check` passes; tech debt entries
created for shortcuts.

## Composing with Domain Skills

Loading a project's domain skills during a request is normal and encouraged. On conflict, fleet
engineering wins on WORKFLOW (stages, gates, claims, audit, DoD) and the domain skill wins on
MECHANICS (code patterns, file conventions, commit and PR formats). If a genuine contradiction
touches a gate, STOP and surface it; never silently pick. Declare which skill applies to which phase
in the exec plan rather than hoping they trigger mid-implementation, because they often do not.
Subagents do not inherit skills you loaded, so anything the evaluator needs domain knowledge to
verify must become a checkable acceptance criterion or go in the spawn prompt.

## Project Initialization

Run `/fleet-engineering:init`. It detects the stack, scaffolds the docs hierarchy, and commits the
process (skill, evaluator, linter, hooks, CODEOWNERS) into the repo. See
`stacks/{stack}/references/project-initialization.md` for stack-specific scaffolding when a stack
guide exists; otherwise proceed stack-agnostically.
